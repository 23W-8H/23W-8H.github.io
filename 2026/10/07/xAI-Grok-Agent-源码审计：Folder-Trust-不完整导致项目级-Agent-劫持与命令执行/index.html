xAI Grok Agent 源码审计：Folder-Trust 不完整导致项目级 Agent 劫持与命令执行

Created2026-10-07|Updated2026-10-07
|Post Views:

一、 摘要与披露背景

本文针对 xAI 官方开源组件 grok-build 进行了深度的静态源码审计。研究发现，系统在处理“不信任”仓库时的 folder-trust（文件夹信任）机制存在缺陷。当用户对某仓库选择“不信任”时，虽然 hooks 和 mcpServers 会被安全丢弃，但同文件中的 prompt_body、system_prompt、tool_config 及 memory 字段却依然被保留并生效，导致项目级 agent 可被恶意覆盖，最终实现任意命令执行（RCE）。

【披露时间线与声明】

  1. 该漏洞（CWE-862）为本人独立在源码审计中发现，并在 Strix 后台环境进行了完整验证。
  2. 已向 xAI 官方 HackerOne 项目提交漏洞报告（#4090846）。
  3. 官方回复：Closed as Duplicate（匹配到了厂商正在跟进或修复的已有问题）。
  4. 鉴于该漏洞属于本地客户端信任模型，厂商已确认并跟进，基于协同披露（Coordinated Disclosure）原则，现决定公开完整技术分析，仅供安全研究和防御参考，严禁用于非法用途。

二、 漏洞详情

  • 漏洞名称：grok-build Project-Agent Folder-Trust Bypass
  • 严重级别：Medium
  • CVSS 评分：4.2 (AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N)
  • 受影响组件：xai-org/grok-build
  • 关键文件路径：crates/codegen/xai-grok-agent/src/discovery.rs
  • CWE 编号：CWE-862 (Missing Authorization)

三、 技术分析与代码审计

1. 信任边界覆盖不全（Folder-Trust Bypass）
在 grok-build 的 folder-trust 机制中，当用户对某仓库选择“不信任”时，检测器确实会拦截 .grok/agents/*.md 等配置，但在同一文件中的 hooks 与 mcpServers 被丢弃后，prompt_body / system_prompt（子代理系统提示）、tool_config（serde 默认值包含终端工具）、permission_mode（bypassPermissions，子代理会话 yolo_mode = true，工具调用不再逐次询问）以及 memory（把仓库内 MEMORY.md 原样拼进子代理提示）却全部照常生效。

2. 执行链与权限提升（TOCTOU 逻辑漏洞）
因为 prompt_body 逃逸了信任边界，攻击者可以构造恶意的 definition.name 为 explore 的配置来覆盖内置子代理。这导致模型会在子代理系统中收到攻击者的指令，并携带 default_agent_toolset() 中的 run_terminal_command（终端工具）和 spawn_subagent 能力。在未显式配置 --permission-mode 的情况下，yolo_mode 会被默认启用，从而实现无询问的任意命令执行。

3. 记忆注入与系统提示劫持
通过 memory 字段，攻击者可以将包含恶意指令的 .grok/agent-memory/explore/MEMORY.md 内容原样拼进子代理的系统提示中。在默认情况下，该字符串会在子代理执行前被解析并加载，构成系统提示注入与命令执行的危险结合。

五、 漏洞影响评估

该漏洞允许恶意仓库在用户明确“不信任”的情况下，依然通过覆盖 explore 项目级 agent 来劫持系统提示和工具集。由于 tool_config 逃逸了信任门控，攻击者成功获取了 run_terminal_command 能力，并在 yolo_mode 下实现了无询问的命令执行。此外，通过 memory 注入，攻击者可以在系统提示中执行任意指令，持久化影响严重。

六、 修复建议（Remediation）

针对此结构性缺陷，建议从以下维度进行修复：

  1. 纳入统一的 Folder-Trust 门控：将 prompt_body、tool_config、permission_mode 和 memory 字段，与 plugins、roles-personas、AGENTS.md、skills 保持一致的 folder-trust 门控，而不是仅门控 hooks 和 mcpServers。
  2. 改变信任模型（Fail-closed）：在 discover_agent_definition 中引入 project_trusted 参数，未显式授予信任时，直接跳过 load_project_definition_by_name，让未知来源的 agent 定义回落到内置版本。
  3. 权限模式显式化：确保 yolo_mode 不会被默认启用在被覆盖的项目级 agent 定义上。
  4. 记忆注入防护：确保 memory 字段在仓库处于不信任状态时，不会被原样拼接进系统提示。

七、 总结与声明

该漏洞为独立发现，基于 xAI HackerOne 项目将该风险标记为 Duplicate，本人已按照协同披露原则对此技术细节进行公开。本文为原创技术研究，首发于个人博客：https://23w-8h.github.io/
